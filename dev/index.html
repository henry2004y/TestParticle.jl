TestParticle.jl ​

TestParticle.jl is a flexible tool for tracing charged particles in electromagnetic or body force fields. It supports three-dimensional particle tracking in both relativistic and non-relativistic regimes.

The package handles field definitions in two ways:

  • Analytical Fields: User-defined functions that calculate field values at specific spatial coordinates.

  • Numerical Fields: Discretized fields constructed directly with coordinates or using Meshes.jl and interpolated via FastInterpolations.jl.

The core trajectory integration is powered by and tight to the DifferentialEquations.jl ecosystem, solving the Ordinary Differential Equations (ODEs) of motion.

To accommodate different performance needs, the API provides:

  • In-place versions: Functions ending in !.

  • Out-of-place versions: Functions optimized with StaticArrays. Note that this requires the initial conditions to be passed as a static vector.

For a theoretical background on the physics involved, please refer to Single-Particle Motions.

Usage ​

Familiarity with the DifferentialEquations.jl workflow is recommended, as TestParticle.jl builds directly upon its ecosystem.

The primary role of this package is to automate the construction of the ODE system based on Newton's second law. This allows users to focus on defining the field configurations and particle initial conditions. For practical demonstrations, please refer to the examples.

In addition to standard integrators, TestParticle.jl includes a native implementation of the Boris solver. It exposes an interface similar to DifferentialEquations.jl for ease of adoption. Further details are provided in the subsequent sections. Check more in examples.

Parallel Scaling ​

TestParticle.jl supports multithreading, distributed computing, and multi-node parallelism for ensemble simulations on CPUs. The following aggregate throughput was obtained on Perlmutter CPU nodes (2x AMD EPYC 7763, 128 physical cores per node). Each ensemble traces 16384 particles for 250000 Boris steps in a uniform magnetic field, saving 100 points per trajectory. Every point is the median of repeated runs, and the error bars span the fastest and slowest repetition.

  • Multithreading: EnsembleThreads() over 1 to 128 threads in one process.

  • Distributed: EnsembleDistributed() over 1 to 128 worker processes on one node.

  • Multi-node: EnsembleSplitThreads() with one worker per node, each worker running 128 threads, over 1 to 8 nodes.

The two single-node strategies track each other within a few percent and reach about 1.1 billion particle-steps per second on 128 cores, close to 60 percent of the single-core rate extrapolated linearly; the rest goes to the lower clock an all-core load draws. Multi-node carries on past one node and reaches 2.7 billion particle-steps per second across 8 nodes, but its one-node point sits well below the single-process runs, since EnsembleSplitThreads gathers every trajectory back to the master process, a cost the shared-memory path does not pay.

Reproducible scripts and the recorded measurements live in benchmark; render the figure with benchmark/plot_scaling.jl cpu.

GPU Performance and Multi-Backend Scaling ​

TestParticle.jl provides vendor-agnostic GPU acceleration via KernelAbstractions.jl. Passing a GPU backend such as CUDA.CUDABackend(), AMDGPU.ROCBackend(), Metal.MetalBackend(), or oneAPI.oneAPIBackend() to solve(prob, Boris(), backend) executes the Boris pusher kernels directly on hardware accelerators.

Benchmark Environments:

  • Workstation (Consumer GPU): Intel Core Ultra 7 265K (20 cores, 20 threads), NVIDIA GeForce RTX 5070 (12 GB GDDR7)

  • HPC Node (Datacenter GPU): NERSC Perlmutter node, AMD EPYC 7763 (128 threads), NVIDIA A100-SXM4-40GB

Reproducible benchmark scripts are available in benchmark/compare_boris_backends.jl.

Key observations from the scaling throughput:

  • CPU Multithreading Contention ( ): In the analytical field, CPU Threads throughput drops from ~1,000 M steps/s at   to ~380 M steps/s at  . This slowdown is driven by host memory management: assembling 100,000 separate ODESolution wrapper objects across 128 threads creates heavy heap allocation contention and garbage collection (GC) pressure. By contrast, KA CPU batches particle states and maintains ~4,100 M steps/s.

  • GPU Default API Bottleneck ( ): The default GPU API curves for FP32 and FP64 peak near 100,000–500,000 particles and then decline. While the GPU integrates millions of particles in a few milliseconds, the CPU host spends hundreds of milliseconds packaging up to 5,000,000 individual ODESolution Julia objects.

  • Unlocking Full Hardware Throughput with Raw Output: Switching to raw_output = true and a bulk initial state matrix (u0) eliminates all per-particle host object allocations. Particle states remain in contiguous matrix buffers, allowing GPU FP32 throughput to scale continuously to over   particle-steps/s at 5 million particles.

Because Boris integration holds particle coordinates and velocities entirely in GPU registers throughout the step loop, the kernel performs zero DRAM reads or writes between and .   • Datacenter GPU (A100): Hardware ALUs are engineered with a full-rate 2:1 FP32:FP64 ratio. The Boris pusher achieves ~100% of the peak theoretical vector compute in both precisions, yielding an exact 2.00x speedup for FP32 over FP64.

  • Consumer GPU (RTX 5070): Consumer GeForce architectures feature a 1:64 hardware ALU rate for FP64. While FP32 delivers exceptional compute (31.2 TFLOPS, >80% of peak), FP64 suffers a 62.4x slowdown due to this hardware throttle.

  • Numerical Grid Interpolation: Evaluating discrete grids ( grid) transitions the bottleneck from pure ALU compute to GPU L1/L2 cache read bandwidth during trilinear interpolations, sustaining 55.5 G steps/s on the A100 and 48.2 G steps/s on the RTX 5070.

Precision Considerations: Float64 vs Float32 ​

TestParticle.jl supports both double precision (Float64) and single precision (Float32) tracing. Supplying Float32 coordinates, velocities, or time span automatically promotes the simulation parameters, physical constants, and equations to single precision.

Advantages of Float32 ​

  • Consumer GPU Throughput: Consumer-grade GPUs (e.g., NVIDIA GeForce RTX 30/40/50 series) feature a 1:64 FP64 ALU throughput throttle. Where single precision is physically acceptable, switching to Float32 unlocks the full hardware compute rate, yielding over 60x faster pure kernel execution. On datacenter GPUs (e.g., NVIDIA A100), Float32 yields the theoretical 2x speedup over full-rate FP64 ALUs.

  • Lower Memory Footprint: Halves VRAM and host memory consumption for trajectory buffers and 3D electromagnetic grids, reducing memory bandwidth pressure.

  • Reduced Host Overhead: Memory allocations and data transfers across the PCIe bus are halved in size.

Trade-offs and Limitations of Float32 ​

  • Accumulated Numerical Drift: With 24 bits of mantissa (~7 significant decimal digits), rounding errors accumulate over long integration periods ( gyro-orbits), potentially leading to phase errors or slight artificial energy drift in non-integrable fields.

  • Dynamic Range / Catastrophic Cancellation: In unnormalized SI units with large coordinate baselines (e.g. planetary magnetospheres where   m, but gyroradii or step increments are in centimeters or meters), Float32 suffers from catastrophic cancellation in spatial increments.

Computing Resource and Scaling Guidelines ​

Based on our CPU and GPU scaling benchmarks across problem sizes, architectures, and precisions:

Problem ScaleRecommended Backend & ConfigurationRationale
Small Ensembles( )CPU Serial or EnsembleThreads()Low particle counts cannot saturate GPUs; GPU initialization and kernel launch latency dominate runtime.
Medium Ensembles(  )EnsembleThreads(), KA.CPU(), or GPU (default API)Both multi-threaded CPU and GPU scale efficiently. Standard ODESolution wrapper objects allow full SciML ecosystem integration without noticeable allocation bottlenecks.
Large Ensembles( )GPU Backend with raw_output = true and bulk u0 matrixAvoid default per-particle ODESolution wrappers. Allocating heap objects on the host creates severe garbage collection contention. Raw matrix output bypasses host overhead, allowing GPUs to sustain particle-steps/s.

  • Precision Guidelines (Accuracy First):

    • Prioritize Numerical Accuracy: Never sacrifice necessary physical precision for execution speed. Use Float64 by default for single-particle orbits, long integrations ( gyro-orbits), and planetary-scale coordinate baselines (  m with small step increments) to avoid catastrophic cancellation and numerical drift.

    • When to Use Float32: Single precision should only be used when physical error tolerances allow, such as large statistical ensembles using normalized dimensionless units (e.g., coordinates scaled by gyroradius or ion inertial length).

    • Hardware Implications:

      • When Float64 is required, datacenter GPUs (A100/H100) or CPU clusters are the ideal targets, as datacenter GPUs maintain full-rate FP64 ALUs (incurring only an expected ~2x compute difference relative to FP32).

      • Consumer GPUs (GeForce RTX series) throttle FP64 ALUs to a 1:64 rate. While they execute Float64 with full mathematical correctness, hardware throughput is restricted. When FP64 is needed, choose datacenter GPUs or multi-core CPUs rather than downgrading precision to Float32.

  • Electromagnetic Field Grids: For discrete numerical grids, use prepare to generate device-native GPUGrid3D structures. This leverages hardware registers and L1/L2 cache for trilinear interpolation and avoids host-side interpolation overhead.
